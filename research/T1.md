# Why Nectar had preview slots

**The cap was there because 12 was an early default, not because the host ran out of anything at 12.** The first specification (`7f1b191`, 18 July 2026) states 12 without a calculation; the first state implementation (`576002d`) copies it. History does not explain why that particular number was chosen. Decision D25 later assumes twelve previews when justifying the port budget. Main already removed the count refusal in `6ee96ca` (22 October), replacing it with available-memory admission.

The old software is still running: the live daemons on metal-1, metal-2 and metal-3 identify their executable as `db834e1`, which still has the default of 12 and enforces it. Seven hosts report exactly twelve serving previews. That makes the Asterlode report credible; the build evidence does not establish each host's effective configuration.

## What this change removes

- The default 100-port walls: upstream becomes **4100–65535**, mesh **8443–65535**. Exact saved old-default pairs migrate on read. Other custom bounds stay unchanged. The relay accepts the expanded mesh range.
- Collisions with recorded app/proxy/dependency/mesh ports and existing Serve entries during web allocation. Active listeners on every local interface are checked; bind probes remain loopback-only. Unsupported IPv6 does not make every port unavailable.
- Accidental use of **443**, pack/remote ports **8440/8441**, and relay control/verification ports **8450/8451**, even with a bad range. These service ports are also refused as public relay upstreams.
- An unsafe cleanup inference: with a range larger than 100 ports, doctor leaves unrecorded entries outside the legacy ranges ambiguous. Port numbers alone do not prove ownership.

No shared static server, waking, eviction or placement is implemented here. The available-memory policy remains: **256 MiB plus min(1 GiB, RAM/8) reserve**, so on this host a new web preview needs at least 1.25 GiB available. The RAM-derived `serving_web_limit` value is an estimate, not an enforced count.

## What remains for placement and rollout

Real limits remain memory, finite available TCP ports, app/dependency cost, descriptor/process limits, disk, and Tailscale/ACL behavior. Existing `E_QUOTA` and `E_PORTS` are the capacity signals for T5. No new host-total count is imposed. At this architecture's current cost, app/proxy ports and Node RSS grow per running preview; T2/T3 change those costs.

Deploying code is still necessary: updating this branch does not update the three confirmed old daemons. Relayd must also be upgraded before higher public-preview ports work. The cross-node port-25000 request proves the live policy permits that specific metal-3→metal-2 connection; it does not establish policy for other hosts or devices. No ACL was inspected or edited. Narrow ACLs must deliberately be adjusted by the operator.

Two tradeoffs remain explicit: migration silently widens a configuration exactly equal to the old defaults, even if it was deliberately pinned; and a wide allocator can claim a currently unused port that another service expects to use later. Active services are skipped, but Nectar cannot infer future reservations. Use nondefault custom bounds when a host has a deliberate partition. The relay still only accepts the caller's own MagicDNS host; its numeric range is not proof a service belongs to Nectar. Trusted publishers can already run arbitrary recipes on their own host.

## Verification and attention

Build, typecheck and lint pass. The focused existing port/state/relay suites pass **29/29**. One full Linux comparison had **358 passed, 8 failed, 3 skipped**; all eight failures also failed against unchanged source on this host (baseline **356 passed, 10 failed, 3 skipped**). The final parallel run had **356 passed, 10 failed, 3 skipped**, adding two fixture response mismatches in deps/remote suites; both suites then passed **75/75** when run serially in a private network namespace. Those cover existing macOS/arm64 assumptions, detached-session fixtures, and lifecycle/ownership fixtures. Initial direct-host tests also encountered preexisting occupied fixed fixture ports; comparison runs used a private network namespace. This is not a fully green suite. No repository verification skill was installed.

Initial mixed-build and unavailable-control-socket probes were discarded or superseded by verified routed runs. No capacity claim relies on them. Claude Opus 5.5 independently audited the diff and decision trail; its remaining attention points are the silent saved-default migration, future port reservations, rollout/ACL coverage, and lack of a macOS real-host run. Its wildcard-bind and relay service-port findings were fixed. No critical findings remained after those corrections.
