# T12 — make least-recently-viewed recovery checkable

Nectar now records every capacity recovery decision in `capacity.jsonl`: ordered candidate list, effective view time, live/persisted/publish-fallback source, persisted view time, eligibility and lock skips, chosen previews, pressure code/resource, and the unchanged `slept_previews` field. Both publish and wake use the same decision path. Recovery logging is serialized per home and rotates at log_max_bytes with two previous files using the existing recoverable rotation. Tailnet-port and no-eligible refusals are logged too. A candidate whose view changes while acquiring its lock triggers a fresh ranking before anything sleeps.

## Diagnosis

The exact historical reasons for T7's p10/p05 selections are not recoverable: that surviving log contains no candidate, lock, route or view-source snapshots. This is a limit, not evidence those choices were correct.

A single run of the same 15-preview restart sequence reproduced an incorrect choice here: view p01 through p15 in order over their real returned HTTPS URLs, then wake p16; p03 slept instead of p01. The new diagnostic record showed p03 using its old persisted timestamp while p01/p02 had fresh live views. A route snapshot showed Serve still pointed at the app ports immediately after daemon hello. Startup opened control before restoring routes, and parallel Serve edits exhausted four ETag retries. Some curls therefore bypassed the viewing proxy; later restoration could not recover those missed views. See `docs/evidence/T12-before.log` and `T12-before-routing.log`. The four-preview version passed; the 15-preview version exposed the startup race. Diagnostic code changed logging only before that red run.

The older T5 fixture also failed here because its fixed 24-port range exhausted during its first twelve publishes, before its pin/stream setup. Its p03 assertion therefore assumed more capacity than remained. The new fixture starts with a wide private range and creates port pressure by narrowing to an occupied fixture-owned port, so it knows exactly which resource is scarce.

## Changes

Serialize Serve edits inside a process, retaining ETag retries for other processes. Restore proxies/routes before opening daemon control and remote listeners. Shutdown handlers are installed before startup, and control opens before app revival and the potentially slow initial proof GC. The fixture simulates a reboot for one own app (pre-boot started_at, stop its own PID, delay new readiness 2.5s) and proves the control socket is ready while that app port is still closed. Serve serialization covers both LocalAPI and CLI fallback, although live evidence here is Linux LocalAPI; CLI behavior is covered by the required suite.

A view means a real request from a person or agent through the preview URL, including plain curl and ongoing request activity. Nectar's own readiness checks and proxy probes do not count. Wake itself no longer stamps a view. Persist `last_viewed_at` separately from `last_opened_at`, preserving it across republish; use the freshest live/persisted view for recovery. Disk writes remain throttled while the live map updates on every actual request. Existing records without this field and never-viewed previews use `published_at`, explicitly documented in SPEC and DECISIONS. The new timestamp is optional; no store migration is required. Live-only views can still be lost on daemon restart because persistence remains throttled.
