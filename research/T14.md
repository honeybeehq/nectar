# Publish and wake under port-lock contention

The machine port lock now waits up to 30 seconds, polling at 50ms, instead of immediately returning E_BUSY. The timeout names the port lock and explains that another publish, wake, or recovery still holds it. Only acquisition retries: the operation executes once, and its errors propagate unchanged. A monotonic clock bounds acquisition waiting. HTTP wake preserves this timeout message and does not restart its existing E_BUSY retry loop after the bounded wait expires.

## Lock paths and ordering

All direct machine--ports acquisitions found with `rg 'machine--ports|PORTS_LOCK' src`:

| Caller | Work | Lock order |
|---|---|---|
| service.provisionDeps | Allocate Docker Postgres ports and persist claims | environment → ports |
| service.withCluster | Local Postgres cluster allocation | environment, when applicable → cluster → ports |
| service.allocateAndSpawn | Eager runtime startup, lazy registration and wake allocation | environment → ports |
| service.assignProxyPort | Reserve and persist proxy listener port | ports → environment (nonblocking best-effort) |
| shared-static.ensureSharedStatic | Singleton allocation, startup/recovery and route setup | environment, when publishing → ports → static |

`StateStore.acquireLock` uses exclusive file creation, checks whether a recorded holder is alive, and throws E_BUSY with `details.lock` for an occupied lock. `withLock` previously propagated that immediately. Putting the port-only policy at this boundary covers all callers without changing environment, cluster or static lock behavior. In particular, proxy assignment must still fail/skip a held environment lock rather than wait while holding ports. There is no ports → cluster/static → ports recursion. Capacity recovery handles E_PORTS/E_QUOTA after the attempted publish/wake has unwound its locks; it tries candidate environment locks without holding ports and skips busy candidates. Waiting on all environment locks would introduce an inverse-order deadlock, so that was rejected.

The existing shared-static outer retry has a 30-second deadline. Its machine-port timeout already consumes that bound and propagates. The HTTP proxy's old 60-second busy retry needed the explicit timeout escape to prevent restarting a completed 30-second port wait and hiding its message.

## Audit corrections and limits

The independent audit found two existing lock-file races amplified by polling: seeing an empty file between exclusive create and PID write, and seeing ENOENT after EEXIST then unlinking a replacement live lock. Lock installation now writes the PID to a unique file in the locks directory, then atomically hard-links it into place. Both initial creation and stale replacement use this path; the returned handle belongs to that linked inode. ENOENT while reading a possible stale lock no longer authorizes unlink. Existing invalid/dead-holder recovery remains supported. A per-resolved-path promise chain serializes acquisition/reclamation within a process, including multiple StateStore instances. It ends before the action starts and before the next poll, so it adds no nested-action lock. The fixture checks eight simultaneous stale-lock recovery contenders never overlap.

The timeout is a **per-port-acquisition** bound, not an overall publish/wake deadline. Existing proxy retries of environment-lock contention can precede port waiting (up to roughly 90 seconds including that separate retry budget); shared-static retries before port acquisition can similarly add time. A port timeout itself is propagated without restarting either loop. Actions already holding a lock are not cancelled. Slow Tailscale work or a stream of competing requests may exhaust 30 seconds; no FIFO fairness is claimed. Daemon proxy reconciliation may consequently wait behind a long holder.

Remaining pre-existing limits: simultaneous reclamation of one dead holder by distinct processes is not serialized by the in-process chain; mixed old/new binaries can still expose the old binary's empty-write window. This task verifies live-holder contention and single-daemon restart reclamation, not a cross-process crash-recovery protocol. Temp files left by a crash before linking are harmless unreferenced files in the locks directory. A persistent/deadline timeout is an intentional clear failure, not a promise that a genuinely wedged or continuously overloaded machine always publishes.
